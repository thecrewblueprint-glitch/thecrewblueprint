# Post-Retrofit Execution Sequence

**Prepared:** 2026-08-31  
**Decision:** After the retroactive field-practice backbone is in the matrix, do not reopen broad domain discovery unless the matrix exposes a genuine missing domain.

## Immediate next — finish the sitewide master matrix

Complete claim-level normalization for the current learner-facing catalog:

1. finish Department Support C1 review/assessment/media edges;
2. backfill all five Department Systems C2 routes;
3. backfill Lead routes;
4. backfill Supervisor routes;
5. backfill Advanced/C3, Production Power Awareness and Production/Coordination;
6. expand question → rationale → claim → source lineage across every scored assessment;
7. expand MEDIA records across existing diagrams/images/video references;
8. attach field-practice evidence during each route pass where it explains real workflow/convention;
9. preserve formal/manufacturer/regulatory evidence as controlling for technical/safety/authority claims.

## Then — generate the evidence audit

Produce data-derived views for:

- unsupported claims;
- over-broad/universal wording;
- contradictory sources/practices;
- qualification/model/jurisdiction-sensitive claims;
- course duplication;
- research-with-no-course competencies;
- built-with-thin-research competencies;
- assessments whose rationale is weak or mismatched;
- visuals needing product/practitioner/rights/accessibility review;
- legacy/superseded routes;
- owner-map bright/muted/gate state.

This becomes the project's **evidence-completeness snapshot**.

## Then — curriculum architecture decision

Only after the evidence snapshot, decide the optimal learner structure.

Questions to answer from data:

- which competencies belong in Fundamentals versus Field Skills;
- which field skills should be standalone micro-courses;
- where C1/C2 should merge or split;
- which departments need branching rather than Course 1 → Course 2 → Course 3 symmetry;
- how Backline / Props / Wardrobe should split after the shared support gateway;
- how Warehouse / Rental Shop should connect to technical career routes;
- whether Rigging/Electrics get awareness/support routes without creating false qualification paths;
- how sector overlays should appear without duplicating whole courses;
- which content should be adaptive, prerequisite-linked, optional or reference-only;
- what the learner-facing career map should expose versus the owner everything map.

The current page/course structure is evidence input, not a protected final architecture.

## Then — course enhancement/build wave

Use the approved architecture plus matrix to:

1. retain strong current lessons;
2. revise over-broad or weakly supported wording;
3. add missing field-realistic context;
4. create missing researched competencies;
5. remove/merge unnecessary duplication;
6. replace or review weak visuals;
7. strengthen scenarios and assessment rationales;
8. keep course completion, observed practice, verified experience and external authorization as separate states.

Visible learner-page changes follow the accepted direct-to-main review workflow; structural/data-system changes remain PR-first.

## Then — human validation

Run separate evidence gates:

### Practitioner validation

Use working stagehands, department techs, leads, venue/shop staff and specialists to review authenticity, boundaries, missing exceptions and field transfer.

### Learner validation

Test comprehension, navigation, confidence calibration, scenario interpretation, retention and transfer with actual learners.

### Customer/buyer validation

Test employers, labor providers, venues, shops, workforce programs and individual buyers for actual value, trust, procurement expectations and willingness-to-pay.

Public forum evidence informs these interviews but does not replace them.

## Then — backend architecture

Once curriculum/evidence states and real user workflows are validated, select/build the backend around stable requirements already identified:

- identity/accounts;
- stable content/course/competency/version IDs;
- lesson/view state;
- knowledge-check state;
- practice/observation records;
- externally verified experience;
- employer authorization kept separate;
- external credentials kept separate;
- source/version provenance;
- role-based permissions;
- accessibility/privacy/security;
- analytics for completion, drop-off, assessment and content-version effects.

Do not select technology merely because current static pages happen to be structured one way.

## Then — controlled release system

After testing establishes realistic content-production and review capacity:

1. define release rings;
2. establish version/rollback/supersession behavior;
3. create backlog buffer;
4. set release calendar/cadence;
5. publish timed course/content updates;
6. monitor learner outcomes and source freshness;
7. feed findings back into the matrix and future versions.

The eventual `audit` branch remains a final owner-review/publication surface, distinct from backend content versioning.

## Short form

**Field reality retrofit → complete master matrix → generated audit → curriculum architecture → course enhancement → practitioner/learner/customer testing → backend → release system.**

This is the preferred sequence because it keeps major structural decisions downstream of evidence instead of forcing the evidence to fit a structure chosen too early.
